# Nido タッチパッドスクロール調査（2026-10-02）

結論：今回の計測では GPU 描画能力や Neovim の待ち行列が大きなボトルネックとは確認できなかった。まず、表示位置を更新するタイミングと、微小な移動量を物理ピクセルに丸める処理を改善候補にする。

調査対象は `main` / `66a74f3`。アプリケーションの実装は変更していない。一時的な計測テストと実行時の計測フックを用い、終了後にテストを削除した。

## 方法と計測範囲

- 別の一時プロファイルで Electron のビルド済み Nido を起動。ユーザーの通常プロファイルには触れていない。
- 4,000 行の Rust 風テキストを `.txt` として表示し、`syntax=rust shiftwidth=4 nowrap` を設定。ブラケット・インデントガイドを含む通常の描画経路を使用。Rust LSP の解析負荷は含まない。
- ウィンドウ 1400×900、Windows の devicePixelRatio は 1.25。
- DOM の WheelEvent を 30 / 60 / 120Hz 相当で約 1.5 秒送信。実際の間隔も記録した。カーソル追従あり・固定の両設定を確認。
- 入力時刻、pixel_scroll 通知受信時刻、Canvas を描く rAF コールバックの開始時刻と CPU 処理時間、main の scroll IPC ハンドラー完了時間、同時に未完了の呼び出し数を記録。
- 実タッチパッドの OS 入力経路、GPU コマンド完了、ディスプレイへの表示完了は計測していない。以下の「Canvas更新」は画面への表示完了を意味しない。rAF 内の CPU 時間にも、その外で動く React 等の処理時間は含まれない。

## 確認できたこと

GPU は有効だった。`2d_canvas` / `gpu_compositing` / `rasterization` はいずれも `enabled`。

カーソル固定設定での結果：

| 項目                                | 約60Hz・2px入力 | 約120Hz・12px入力 |
| ----------------------------------- | --------------: | ----------------: |
| Canvas描画コールバックの平均CPU時間 |        約0.61ms |          約0.72ms |
| 入力→Canvas更新の平均時間           |        約6.18ms |          約6.22ms |
| main側scroll完了の平均時間          |        約1.24ms |          約1.66ms |
| スクロール中の平均描画間隔          |       約15.83ms |          約9.72ms |
| 描画間隔の95パーセンタイル          |        約25.5ms |          約17.0ms |
| 同時に未完了のscroll呼び出し最大数  |               1 |                 1 |

rAF の平均周期は約8.4〜8.6ms。それに対して、約120Hz入力でも描画間隔は平均9.72msで、更新周期にばらつきがあった。ただし、これだけで実際のディスプレイの FPS や VS Code との FPS 差は確定できない。

追従設定の別計測でも main 完了は平均約1〜2msで、未完了呼び出しは最大1〜2件、計測終了後の未処理入力は0件だった。前の説明の「Neovimの処理待ちが主因」という推測を、今回の結果は支持していない。

微小入力には明確な段差がある。0.1px × 180回の入力では165回の描画サンプルに対して、最初の行画像のY位置は24種類だった。移動位置を物理ピクセル単位で丸めるため、複数回入力しても同じ位置を描く。その後まとめて約0.8 CSS px動く。これはゆっくり指を動かす場合や慣性スクロールの終わりで目立つ可能性がある。通常速度のスクロールの主因であるかは未確定。

## コード上の理由

1. `src/renderer/src/Editor.tsx:129`：wheelごとに直ちにIPCを送る。renderer側だけで表示位置を先に更新する処理はない。
2. `src/main/session.ts:353`：共有inputQueueで順番に処理し、Luaスクロールと追加の `nvim_eval('1')` 完了を待つ。
3. `src/main/sessionEvents.ts:36`：行データ・小数オフセット・カーソルをまとめて公開する。原子性のための仕組みであり、単純に待機を削除すると表示がずれる恐れがある。
4. `src/renderer/src/hooks/useEditorRendering.ts:355`：タッチパッド経路ではdirectScrollを設定し、通常のスクロールアニメーションを使わない。
5. `src/renderer/src/grid.ts:310` / `408`：スクロール位置と行画像の描画位置を物理ピクセルに丸めている。小数を保持するだけでは、最後の描画位置の丸めが残る。
6. `resources/nido/session.lua:126` と `src/renderer/src/hooks/useWorkspaceSessions.ts:24`：スクロールに伴う状態通知でReactの状態も更新される。120Hz・12px・180入力の計測ではstate通知は266件。CPU負荷への寄与は別途計測が必要。

VS Code の公開ソースでも、通常のwheelアニメーションは物理マウスホイールとして分類された入力だけが対象で、タッチパッドは通常 `setScrollPositionNow` を使う。「補間アニメーションがないこと」だけを原因とは言えない。参考：[scrollableElement.ts](https://github.com/microsoft/vscode/blob/main/src/vs/base/browser/ui/scrollbar/scrollableElement.ts#L501-L512)。今回VS Codeを同条件で実測したわけではない。

## 改善の優先順

1. **表示位置をrendererで即座に更新し、Neovim同期をまとめる。** 入力の合計移動量を保持し、rAFで描画。Neovimへの同期はフレーム単位に合算し、処理中も後続入力の合計だけ保持する。ローカル表示とNeovimの返答が二重に適用されないよう、どこまで同期済みかを管理する。通信待ちで表示更新が遅れる機会と、過剰な呼び出しを減らす狙い。今回の低負荷計測では待ち行列が溜まっていないため、大幅な速度向上は保証できない。
2. **行画像の移動に小数ピクセルを許す試作を比較する。** 文字画像の生成位置は従来どおり鮮明に保ち、表示時の移動だけを検討。微小移動の段差を減らす狙い。ただし文字がぼける可能性があり、125%・150%表示で静止時と移動時を見比べて採用を決める。ガイド・カーソルも同じ座標で動かす。
3. **スクロール時の状態通知とReact更新を減らす。** 変わらない情報は再送・再更新を省き、スクロール率などは最新値をまとめる。入力、診断、バッファ切り替えの通知は維持する。余分な負荷を減らす候補で、現状の主因と断定する根拠はない。

まず1と2を小さく試し、同じ計測と実タッチパッドで比較するのがよい。追加RPCの単純削除、GPU方式の全面変更、長いイージングアニメーションの追加は最初の対策にはしない。

実機での確認では、ゆっくり・速く・慣性終盤・上下反転の入力を記録し、入力間隔とCanvas更新間隔を比較する。折り返し、fold、CodeLens、EOF、カーソル固定、相対行番号、ガイドとの位置一致も確認する。
