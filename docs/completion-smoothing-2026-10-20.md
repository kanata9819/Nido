# 補完ウインドウの点滅・表示遅延（2026-10-20）

対象はWindows、変更前HEAD `a8509a29fd52347c9bf50046d0415f4e891d99e2`。前回の候補一覧の仮想化を維持し、入力から候補表示までと更新中の見え方を調査・修正した。

## 原因と変更

| 確認した処理                                                         | 変更                                                                                   |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 文字入力・Backspaceのたびに30ms待ってから新しい補完を要求            | 次のイベント処理で実行。同じ処理中の連続編集は引き続きまとめ、最新の内容だけ要求する   |
| 候補の更新待ちで全候補行の不透明度を1から0.5に変更                   | 明るさを1に固定。更新中のARIA状態・クリック・Tab・上下移動の制限は維持                 |
| 初回表示に共通の130msフェードイン                                    | 補完ウインドウだけ最初のフレームから通常の明るさで表示。終了時のフェードは維持         |
| ネイティブによる古い候補の絞り込み通知が更新待ち状態を解除する       | リクエスト完了まで更新待ちを保ち、ウインドウのDOM・位置・高さを保持                    |
| キャンセルを無視して後着する応答が最新候補に混ざる                   | 最新要求・バッファ・カーソル・本文・入力モードを照合し、古い入力中の応答を破棄         |
| 候補が隠れた後にもNeovimの候補キャッシュが残り、新しい結果へ合流する | 再取得とCtrl+Spaceの前にネイティブ候補を空にし、候補ゼロで古い一覧が復活する問題を解消 |

遅い応答を設定した実Electron試験では、変更前もDOM自体の削除・再作成は毎入力では起きなかった。半透明への切り替えと初回フェードが、明るさの変動と表示の遅さを生んでいた。表示の連続性はDOMの同一性だけで判断せず、描画フレームごとの不透明度と終了状態も調べた。

Tab確定による本文の変更を次の入力と扱い、補完が再び開く動作も修正した。確定時の本文とカーソルを記録し、次の編集まで自動要求を開始しない。

応答の照合は入力中の補完に限定しており、言語パックなどが通常モードで直接行う補完API要求は従来どおり完了する。初回のフェード変更は他のカード・コマンド補完へ適用していない。

## 検証

- 修正前のElectronで不透明度1を維持する回帰テストが失敗することを確認。最終コードでは、90ms応答のサーバーで文字入力5回・Backspace1回を繰り返す試験を3回実施。計492フレームで不透明度1、DOM再作成0、終了状態0を確認。Tab確定後も、遅い応答の時間を超えて閉じたままになることを確認。
- 最新の応答が先着し、古い応答が180ms後に届く試験で、古い候補が追加されることを再現。修正後は最新版のみを保持し、候補ゼロでも古い候補が復活しないことを確認。
- ブラウザーの回帰試験で、初回の即時表示、更新中のTab・Ctrl+N抑制、古い絞り込み通知、DOM・位置の保持、候補なしでの終了時フェードを確認。
- 実TypeScriptサーバーによる自動補完・Ctrl+Space・Tab・上下移動・クリック選択・Backspace・CodeLens追従・診断表示の既存試験も確認。

最終Electron試験での最初の文字から表示までの観測は、10ms応答の試験用サーバーで26.0 / 34.1 / 32.8ms、既存の実TypeScriptサーバー試験で25.8 / 28.5 / 25.0ms。前者は最初の画面フレーム、後者はDOM追加を観測しており、異なる測定として扱う。

前後のNeovim通知順の記録はGit対象外の `.downloads/completion-audit-20261020-before.json` と `.downloads/completion-audit-20261020.json`。最初の計測では、10ms応答のサーバーに対する最初の文字から候補通知までが56.3ms、固定待機を除いた試験では13.8msだった。これは各1回の合成入力の観測で、実プロジェクト全般の保証値ではない。
