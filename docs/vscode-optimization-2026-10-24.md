# VS Codeを参考にした表示・描画の改善（2026-10-24）

Windows上の `04e203f` を変更前として、構文色、Canvas描画、カーソル移動時のLSP状態取得を調査しました。

## 表示

インストール済みの公式VS Codeに含まれる[TypeScript文法](https://github.com/microsoft/vscode/blob/main/extensions/typescript-basics/syntaxes/TypeScript.tmLanguage.json)と[Dark+のテーマ定義](https://github.com/microsoft/vscode/blob/main/extensions/theme-defaults/themes/dark_plus.json)（Dark Modernも継承）を照合しました。`as` と `satisfies` は制御キーワードの紫 `#C586C0`、`as const` の `const` は修飾子の青 `#569CD6` に合わせます。独自の型名は緑を維持します。文字列・コメント・同名プロパティは制御キーワードとして扱いません。

## 処理の削減

[VS Codeの構文ハイライト最適化の解説](https://code.visualstudio.com/blogs/2017/02/08/syntax-highlighting-optimizations)では、色を共有し、解決済みのスタイル情報を再利用する設計が紹介されています。Nidoでも描画ごとのハイライトIDから前景色・背景色・フォント・装飾色を一度だけ解決します。フレームをまたぐスタイルキャッシュは追加していないため、次の描画でテーマ・ハイライト定義・フォントの変更を反映します。

LSP状態取得は、全クライアントと現在のbufferに接続したクライアントを別々に列挙していました。同じ最新の一覧から両方を作るように変更し、初期化・接続先・進捗・終了の状態を保持するキャッシュは追加していません。

| 計測条件                                           |   変更前 | 変更後 |
| -------------------------------------------------- | -------: | -----: |
| 160列×45行、同じ色の初回描画：16進色文字列への変換 | 14,400回 |    2回 |
| 同条件、1文字の編集を20回：16進色文字列への変換    |  6,400回 |   40回 |
| 40回のカーソル状態通知：LSPクライアント一覧の取得  |     80回 |   40回 |

Canvasの時間計測は、変更前と変更後を交互に8組実行し、組ごとの1描画当たりの時間の中央値を比較しました。全画面描画は各組30回、1行の編集描画は各組300回です。Canvas処理の完了を含めるため、画素の読み戻しを含みます。

| Canvasの局所計測           | 変更前の中央値 | 変更後の中央値 |
| -------------------------- | -------------: | -------------: |
| 色付きテキストの全画面描画 |       26.188ms |       23.202ms |
| 色付きテキストの1行編集    |        0.598ms |        0.558ms |
| 既定色テキストの全画面描画 |       18.235ms |       16.580ms |
| 既定色テキストの1行編集    |        0.352ms |        0.325ms |

この条件では描画処理が約7〜11%短くなりました。合成入力に対するローカル計測で、アプリ全体のCPU使用率、入力遅延、FPSの改善率を示すものではありません。LSPの一覧取得回数の削減も、言語サーバーのCPU使用率とは別の指標です。

## 検証

変更前と変更後の描画を、100 / 125 / 150 / 200%倍率、通常 / 半透明テーマ、10種類の状態で比較し、80比較すべてでRGBAの不一致は0でした。日本語・結合文字・絵文字、太字・斜体、CodeLens、反転色、診断、単語・括弧の強調、フォント・テーマ・ハイライトの変更を含みます。

単体・統合テストは225件成功、失敗0でした。WSL実機テスト1件は、実行先のLinux環境が未指定のため未実行です。描画・スクロール・カーソル・編集の関連画面テスト21件、アプリの型チェック、変更したコードのlint・書式検査、production buildが成功しました。

ビルドしたアプリを専用のテストプロファイルで起動し、TSXの実際の色、通常の編集・保存、日本語・絵文字を含むスクロール、キーボードでの先頭復帰、再起動後のファイル・内容復元を確認しました。未処理のrendererエラーは0件でした。これらはローカルでの検証です。
