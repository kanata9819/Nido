# j/k 長押し中のスクロール

前回のカーソル追従の計測は、画面内の移動が対象だった。今回は画面の端を越えてスクロールする経路を調べた。

## 変更

- 連続した j/k 移動では、進行中のスクロールを中断せず表示位置を引き継ぐ。
- スクロールの追従時間を更新間隔に合わせる。単発操作・行削除の従来の演出時間は維持する。
- 演出だけが進むフレームでは、描画済みの画面を再利用する。Neovimの更新、カーソル点滅・フォーカス、表示サイズの変化では再描画する。
- UIアニメーション・滑らか移動の設定は変更しない。

## ローカル計測

独立したElectronプロファイルと約1,000行のRustテストプロジェクトを使用。修正後はrust_analyzerの接続も確認。初期解析を10秒待ち、300行目を中央に表示してから、j/kを33ms間隔で各100回入力した。UIアニメーションはON。

| 指標                       | 修正前 j / k    | 修正後 j / k    |
| -------------------------- | --------------- | --------------- |
| Canvas画像描画の呼び出し数 | 25,447 / 24,980 | 11,785 / 11,361 |
| 上記呼び出し数の削減率     | —               | 54% / 55%       |
| rAFコールバックの中央値    | 0.6 / 0.6ms     | 0.3 / 0.2ms     |
| 入力から状態通知までのp95  | 9.0 / 10.4ms    | 9.7 / 13.2ms    |
| 到達行                     | 400 / 200       | 400 / 200       |

これは1つのテストプロジェクトでの計測。描画量の削減を確認したが、入力遅延の改善や、ユーザーの実プロジェクトで感じる強い重さの解消を証明する値ではない。

## 回帰確認

キャッシュ利用時と通常描画を、100/125/150/200%の拡大率、通常・透過背景、上下・左右・削除の演出、途中の画面更新・カーソル変更・アニメーション無効化で比較し、ピクセル差分は0。実際のレンダラーでも、長押し中のキャッシュ再利用、画面更新時の再描画、Insertモードの入力による中断を確認するテストを追加した。

計測スクリプト・CPUプロファイル・生データはローカルの `logs/held-scroll-*` に保存。テストで使ったプロジェクトとプロファイルは終了後に削除する。

## 実ファイルと相対行番号での追試

ユーザーから「Rust の `parser.rs` では依然重いが、ターミナルを開くと軽い」と報告があった。画像の相対行番号を再現すると、同じファイルのコピーでも重さを再現できた。従来の測定は既定の絶対行番号であり、この条件を見落としていた。

相対行番号が変わるたびに各表示行の Canvas を破棄・再作成していた。スクロール時は保持する行データをコピーするため、その経路でも画像を再利用できなかった。また、物理ピクセルに揃った行にも、分数ピクセルの明るさ補正用テクスチャを準備していた。表示行数が増えると、画像の作成・破棄と GPU 転送が増幅する。

変更は次のとおり。

- 変更した行は既存の Canvas に描き直し、半透明の行は物理ピクセルの全領域を消去してから描く。
- スクロールで行データをコピーするときは、表示用画像の所有権も移す。保持した元のセルは変更せず、再表示時に必要なら画像を再作成する。
- 物理ピクセルに揃った行の補正用 GPU 転送を省き、分数位置で初めて必要になったときに準備する。分数位置での補正とキャッシュは維持する。

独立した一時プロジェクトに `C:\dev\39_noise\chibi\crate\chibi\src\esc\parser.rs` の内容をコピーし、相対行番号・滑らかなカーソル・UI アニメーションを ON にして測定。元のプロジェクトは変更していない。1488×960 の論理ウィンドウ、125% DPI、165Hz、約45行を表示し、100行目から j/k を33ms間隔で各80回入力した。rust_analyzer の接続を確認したが、元のプロジェクト全体の解析状態は再現していない。作業中に元ファイルの更新があったため、最終比較では内容を固定し、SHA-256 が両版で一致することを確認した（`0b912df9ba89ba486824314d5ede118df763020cf6c6a34b7a8f4c2d385a1595`）。比較用ビルドは HEAD の3モジュールだけをビルド時に読み込み、読み替えが実行されたことも検証している。最後に修正版を再ビルドした。

| 指標                               | 修正前 j / k    | 修正後 j / k  |
| ---------------------------------- | --------------- | ------------- |
| 入力から状態通知までの p95         | 175.4 / 135.5ms | 12.3 / 12.7ms |
| 描画コールバック間隔の p95         | 120.4 / 106.1ms | 10.1 / 17.7ms |
| 補正用テクスチャのアップロード回数 | 2,873 / 2,873   | 675 / 765     |
| 到達行                             | 180 / 20        | 180 / 20      |

最終比較でターミナルを開いて約29行に減らすと、修正前の入力 p95 は11.1 / 61.2ms、修正後は9.4 / 7.9msだった。初回の追試でも、ターミナルを開いた条件は11.5 / 10.3ms、ターミナルを閉じてウィンドウだけを同じ高さに縮めた条件は11.0 / 9.9msで、表示行数による差を確認できた。初回の修正後は9.2 / 7.2msと9.3 / 8.9ms。大きな画面に戻した追試でも12.2 / 9.7msで、修正前の343.8 / 166.5msの滞留は再現しなかった。これらの初回値は、最終の内容固定比較とは別の実行である。

追加の回帰テストは、相対行番号を伴う上下80回の移動で新規行画像が80枚以内であること、整数位置で補正用 GPU アップロードがないこと、初回の分数位置で準備した画像を後続フレームで再利用することを確認する。100/125/150/200% DPI と半透明背景では、新規描画とのピクセル比較に相対行番号・保持行・上下反転も含める。

最終ソースで、全レンダラーテスト142件、専用WebGLテスト8件、スクロール・行保持のユニットテスト15件、型検査・ESLint・Prettier・ビルドが通過。通常Canvasバックエンドでのピクセル比較8条件は差分0。実際のElectronでもターミナル開閉の表示と、両方向80回の入力後の到達行・エラーなしを確認した。

SwiftShaderを通常Canvasのピクセル比較にも適用した追加確認では、半透明125/150/200%の3条件で各6/7/10チャンネルの差分が出た。HEADの元コードを別フォルダに読み出して同じ比較を実行し、同じ差分と失敗を確認した。今回の変更による増加はなく、通常Canvasでの比較と専用WebGLテストを分けて評価している。

生データと CPU プロファイルは `logs/viewport-*` に保存。これらは一時プロファイルでのローカル計測であり、ユーザーの開いているアプリでの手動確認、元プロジェクト全体の LSP 負荷、CI・配布版の検証は含まない。
