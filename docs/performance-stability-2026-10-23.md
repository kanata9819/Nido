# Performance and stability audit (2026-10-23)

Windows上の `30cef80` を基準に、入力・描画、Neovim/LSP、ファイル検索、Git、履歴、ターミナルと終了処理を確認しました。すでに導入済みの最適化は維持し、要求の重複、不要なタイマー、大量データの処理に絞って改善しました。

## 比較条件

- Git gutter: 実Neovimで同じbufferへの更新要求を20回送り、`vim.system` の完了だけを保留して要求数を計測します。実Gitプロセスを20本起動する試験ではありません。
- Word highlights: 実Neovimで `CursorMoved` を40回発火し、250msの待機中に保持するタイマー数と最終ハイライトを確認します。
- Markdown preview: 応答を保留した状態で200ms間隔の編集10回と、ウィンドウ非表示中の編集5回を送り、要求数と古い結果の扱いを確認します。
- Problems: 10,000件の診断を表示し、一覧のDOM数と連続選択に伴う再処理を確認します。全件へのキーボード移動、検索、元の診断位置へのジャンプも検証します。長文診断の可変行高は維持します。
- Time Machine: 10版、8,001,749 bytesの履歴JSONを用意し、内容を変更せずに一覧を5回開き、全文読み込み回数と処理時間を比較します。

要求数・タイマー数・DOM数・読み込み量の削減と、アプリ全体のCPU使用率や入力遅延は別の指標です。計測用の遅延応答は最悪時の重複を再現するもので、通常時の通信速度を示しません。

| 対象                                                     |                  変更前 |                 変更後 |
| -------------------------------------------------------- | ----------------------: | ---------------------: |
| 同じbufferのGit更新で未完了のコマンド                    |                    20件 |                    1件 |
| 40回のカーソル移動で追加稼働する単語ハイライト用タイマー |                    40個 |                    1個 |
| 遅いMarkdown取得中・非表示中の編集で未完了の要求         |                    16件 |                    1件 |
| 10,000診断を20回選択移動したときの並び順比較             |               409,959回 |                    0回 |
| 10,000診断を20回選択移動したときの行の再描画             |               200,000行 |                   40行 |
| 履歴一覧を5回開くときのJSON全文読み込み                  | 10回 / 80,017,490 bytes | 5回 / 40,008,745 bytes |

Time Machineの同条件5サンプルは、変更前18.46〜22.57ms、変更後8.25〜12.80msでした。これは模擬Sessionと実LocalHistoryの局所計測です。Neovimからの本文転送はどちらも5回、4,000,005 bytesで維持しています。

診断行は描画時の `severity` 参照を計測し、1行あたり2回の参照から描画行数へ換算しています。旧HEADの `PaletteItems` を同じ画面ハーネスへ差し替えた比較で、参照は400,000回→80回でした。同じ20回の移動と選択確認を含む試験操作は14,230ms→3,493msですが、Playwrightの操作・検査時間も含む参考値であり、入力遅延そのものではありません。

## 改善内容

Git gutterの取得はbuffer単位で実行中の処理を共有し、待機中の更新を最後の1回へまとめます。古いbuffer内容への結果は適用せず、buffer破棄と終了時に実行中の処理を解除します。

単語ハイライトは250msの待機時間を維持し、移動ごとのタイマー新規作成を再利用する1個のタイマーに置き換えます。buffer/windowの切り替え、編集、フォーカス喪失などによる取消条件を維持します。

Markdownは150msのまとめ処理に加え、取得中の要求を重ねず、最新の編集を後続の1回で取得します。ウィンドウ非表示中は取得を止め、再表示時に照合します。

Problemsは診断の整列とフィルターを診断データ・検索語の変更に追従させ、選択だけの変更で一覧全体を再構築しないようにします。行も再利用し、選択の移動では以前の選択行と新しい選択行だけを描き直します。ジャンプ先は元の診断番号と診断versionを使い、サイズ変更時にも選択行を表示します。

Time Machineは保存処理と同じ直列トランザクションから履歴一覧のメタデータを返し、直後の全文再読み込みを省きます。永続的なJSONキャッシュは導入せず、次の操作では履歴ファイルを読み直して外部変更・破損を確認します。

## 検証

`tests/session-performance.test.ts` と `tests/editor-highlights.test.ts` が要求集約、最新HEADと未保存本文、bufferの改名・破棄、Git失敗後の復帰、ハイライトの取消・終了を検証します。`tests/feature-performance.spec.ts` がMarkdownの遅い応答・非表示・切り替え・終了と、診断の処理回数、可変行高、検索・移動・ジャンプ、診断version・workspace・翻訳の追従を検証します。`tests/local-history.test.ts` が保持上限、保存順、外部変更・破損検知、書き込み失敗後の再試行を検証します。

Git gutterの既存テストは、初期の空のsignを見て即座に成功した後、計測開始前から実行中のGit要求が残る場合がありました。集約後の処理を開始前に完了と誤判定しないよう、実際に新しいGit処理が開始し、完了するまで待つよう修正しました。待機上限、外部commitへの定期追従、HEAD確認・本文キャッシュの検査は維持しています。

全単体テストは214件成功、失敗0、WSL実機テスト1件は環境未指定で未実行です。通常の画面テスト184件、起動・復旧・通知タイマーの5回繰り返し40件、SwiftShaderでのWebGL必須検査24件も成功しました。アプリとWindowsテストの型チェック、lint、production buildが成功しています。

最終コードを `dist/performance-stability-validation/win-unpacked/nido.exe` に梱包し、Windows必須43件がすべて成功しました。通常の編集・保存、Git操作とHEADのgutter、診断一覧、Markdown、ターミナル、履歴復元、再起動、外部ファイル同期、スクロールと画素比較を含みます。実行中の既存アプリと出力先を分けています。

## 今回見送った候補

Problemsは10,000件のDOMを引き続き保持します。長文の診断は改行・折り返しに応じて行高が変わるため、固定行高への変更は避けました。初回表示のDOM数を減らすには、可変行高とキーボード・アクセシビリティを維持する仮想化の設計が必要です。

終了時の履歴収集は複数workspaceの本文を並列に取得し、単一の保存キューで待機させます。遅い保存を模擬した8 workspace × 8 buffer × 64 KiBの条件では、最大4 MiBの本文が待機しました。逐次取得なら約0.5 MiBに抑えられますが、独立したNeovimからの取得まで直列になるため、終了時間との比較が必要です。今回は変更していません。

カーソル移動時のLSPクライアント一覧取得にも削減の余地があります。クライアント初期化・終了・attach/detach・進捗表示の無効化条件を整理する必要があるため、今回は変更していません。
