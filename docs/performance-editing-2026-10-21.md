# 編集中の検索カウントと括弧ガイドの負荷削減

基準コミットは `e905397`。入力、カーソル移動、スクロールの既存の改善を確認し、今回追加で負荷を確認した検索件数の計算と括弧ガイドを修正した。

## 原因と変更

- 検索ハイライトが有効なとき、位置が変わるたびに `searchcount(recompute=1)` が全文を走査していた。10万行の検証では1回の中央値が約6.9ms、40回の移動で40回走査していた。
- 全文カウントを即時の位置通知から分離し、近接する操作を最新の位置へまとめた。軽い検索は16ms、重い検索は実測時間に応じて最大80ms待つ。連続操作でも最初の待機から120msを超えたら次のタイマーで実行するため、操作し続けても件数の更新は止まらない。タイマーの実行にはイベントループによる遅れが加わる。
- 件数が更新されるまでは同じ本文・検索条件の直前の値を保持する。本文、検索語、バッファが変わった場合は `Counting…` を表示してから最新の件数へ更新する。Neovimの正規表現、9,999件の上限、1回10msの計算期限は維持した。
- 括弧ガイドは同じ表示範囲・同じスコープ内での移動でも、全ガイドのインデントと画面位置を再計算していた。カーソルだけの通知では、本文の変更番号、表示範囲、ウィンドウの位置・寸法、スクロール位置、括弧索引、アクティブなスコープが同じなら再利用する。Neovimが画面を描き直す場合は毎回再計算する。

## ローカル計測

実際のElectronウィンドウと独立した一時プロジェクトを使用。6万行のテキストに6,000件の検索一致を置き、相対行番号・アニメーションを有効にした。16ms間隔で80回の移動、続いて80文字の入力を行った。入力イベントから対応する位置の状態通知までを計測しており、画面に出るまでの総時間やFPSではない。

比較用のアプリはビルド済みのmain/preload/rendererと同じ依存リソースを使用し、`session.lua` と `nido_brackets.lua` の2ファイルだけを基準コミットの内容へ置き換えた。現在のソースは上書きしていない。

成立した2回の比較の中央値：

| 指標                                   | 変更前 | 変更後 |
| -------------------------------------- | -----: | -----: |
| 検索中の文字入力：位置通知までの中央値 |  9.8ms |  1.6ms |
| 同p95                                  | 16.2ms |  7.6ms |
| 検索中の連続移動：位置通知までの中央値 | 10.7ms |  2.7ms |
| 同p95                                  | 15.8ms | 10.5ms |

両版で最終行380、入力80文字すべての反映、検索件数6,000件、未処理の画面エラーなしを確認。修正後は状態通知がまとまる場合があり、1回目の入力では78件、2回目は79件の途中位置を観測した。キーの欠落を示すものではなく、最終の本文で全80文字を検証している。

3回目の比較は、変更前の検索計算が既存の10ms期限に達して `incomplete=1` になり、完全な最終件数を要求する計測の前提を満たさなかったため不成立として除外した。初期の16ms固定版の比較も最終値には含めていない。テキストだけの大きな検証ファイルでの値であり、Rustプロジェクト全体のLSP負荷や、すべての操作が同じ割合で速くなることを示すものではない。

最終ソースでも、1,000・30,000・100,000行の各ファイルで40回の移動に対する全文検索は40回から1回になった。括弧ガイドは、100回の同一スコープ内移動でインデント取得・画面位置取得が各2,000回から0回になった。処理時間の参考値は約19.0→9.4ms。回帰テストでも、同一スコープ内20回の移動で位置計算がないことを確認し、スコープ切替・横スクロール・編集後の結果を全面再描画と照合している。

別の一時Rustプロジェクトでも、rust-analyzer接続・相対行番号・アニメーションを有効にして `j` と `k` を各80回入力した。最終行180・20へ全入力が反映され、画面エラーはなかった。入力から位置通知までのp95は、変更前11.8/11.5ms、変更後10.3/10.4ms。この比較は各版1回の動作確認であり、小さな時間差だけで一般的な高速化とは判断しない。

生データ・計測用スクリプトはGit対象外の `logs/general-native-*`、`logs/general-input-adaptive-1.*`、`logs/general-input-adaptive-2.*`。比較用のリソースは `.downloads/general-baseline-20261021` に保存した。

## 検証

検索カウントについて、短時間40回の移動が最後の1回へまとまること、位置通知が計算を待たないこと、古い本文・検索語・バッファの計算が届かないこと、検索解除後に復活しないことを確認した。制御した時計と遅い計算でも、待機上限と最終位置の正しい件数を検証している。

- 単体テスト：199件成功、WSL実環境を必要とする1件は未設定のためスキップ。
- Node・Web・Windowsテストの型チェック、Lint、ビルド成功。
- 実際のElectronウィンドウで10件成功。編集・保存、クリップボード、ターミナル切替、検索、補完、Markdown、型情報、クリック位置、ホイール、ワークスペース切替を確認。
- スクロールの連続描画・設定切替を各2回、計4件成功。変更前の比較用アプリでも連続描画の検証を2回成功。

連続描画のテストは最初、変更前と変更後の両方で失敗した。描画コールバックの間隔が伸びても移動量に固定の上限を置いていたため、実際の描画間隔と入力間隔に応じた上限へ修正した。通常の描画間隔では元の上限を維持し、逆方向への移動・総移動量も検証する。失敗時の記録を使った再計算では、遅れたフレームは許容し、静止フレームの後に通常の間隔で跳ぶケースは引き続き検出することを確認した。スクロール本体やアニメーション設定は変更していない。

検証はローカルの開発ビルドと一時プロジェクトで実施。インストーラー、リモートCI、ユーザーの実プロジェクトでの手動確認は今回の実施範囲に含まない。
