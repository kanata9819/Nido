# エディタの性能・安定性監査（2026-10-28）

Windows の v0.4.0（`897c402`）を基準に調査した。既存の最適化・入力順序・表示の互換性を保ち、再現または処理量の計測で確認した問題を修正した。新しい依存ライブラリは追加していない。

既存のキー入力キュー、changedtickと世代による古い結果の排除、LSP状態キャッシュ、局所text edit、要求期限は維持した。行キャッシュは上下各256行、文字幅キャッシュは1,024件、GPU行画像は2画面分のLRUという既存の制限を確認した。正常な経路で再現しなかった部分矩形scrollの共有行破損は、推測で変更していない。

## 確認して修正した問題

| 問題                                                   | 修正と局所比較                                                                                                                                                                                                        |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 新しい色IDの追加でも既存行高のキャッシュを全破棄       | 使用済みIDの再定義時だけ破棄する。160列×45行＋上下各256行に20 IDを追加したとき、無変更セルの文字参照は **1,779,200→0回**。新IDを使う行と既存IDの再定義には追従する。                                                  |
| 折り返し行の上スクロールで再利用可能なbitmapが失われる | `nido_scroll`を伴う全行再通知では旧行画像を保持し、同一行の復元後も使えるようにする。既存Electron試験のglyphs/paintは **916.4→86.2〜89.3**（修正後3回）。閾値は変えていない。                                         |
| 遅いリサイズ中にIPCとPromiseが積み上がる               | 処理中の要求を1件に保ち、完了後に最新寸法だけ送る。20回の変更で待機 **20→1件**、後続は最新寸法の1回。失敗後も最新寸法へ追従し、破棄後は再送しない。main側の既存の世代保護も維持する。                                 |
| コマンド補完が全候補をDOMへ展開                        | コード補完と同様に表示範囲と前後の候補だけ描く。1万候補で **10,000→23 DOM行**。選択行は画面外でもARIA用に保持し、末尾選択・手動スクロール・クリック・候補減少を維持する。                                             |
| 選択やコマンドカーソルの移動でも全UI状態を再転送       | 変更した項目だけ送り、候補配列が同じなら選択番号だけ送る。同じ20操作で候補再転送 **200,000→0行**、JSON換算 **4,384,222→4,002 bytes**。初回・再attach時は全状態を送る。                                                |
| 括弧・Sticky・Gitの古い待機タイマーが残る              | ticketによる結果の無効化に加え、前のtimerを停止・closeする。40回編集後の同時稼働は各 **40→1個**、合計 **120→3個**。buffer unload・終了で解除する。                                                                    |
| 検索カウントの古い待機タイマーが残る                   | 前の検索timerを取消し、検索解除・buffer unload・終了時にも解除する。遅いイベントループを模した40更新で **待機1個・検索1回**。継続入力中の最大120ms待機は維持する。                                                    |
| スクロールの停止判定timerを入力・描画ごとに作り直す    | 1個のtimerと最終入力の期限を使う。8ms間隔の100入力でtimer作成 **102→6回**。最終入力から159msでは停止せず、160msで停止する。通信・補充待ちの40ms再確認は維持する。                                                     |
| CodeLensの低い行をまたぐとピクセル入力の距離が減る     | 画面上の距離を、取得済み行高からNeovimの行数へ逆変換する。標準行と低い行を跨ぐ **90px入力→85px移動**を **90px→90px**へ修正。未取得行は標準行高を使い、境界判定は変換後に行う。                                        |
| 横スクロールで内部カーソルが動くと単語の強調が変わる   | 編集位置を保持している間は既存の強調を維持し、古い強調要求を取り消す。表示用の内部カーソルを40列移した実Neovim試験で、`alpha`の強調が消える旧挙動を再現し、修正後は維持される。キーボード操作で通常の強調へ復帰する。 |

括弧・Sticky・Git・検索の`vim.defer_fn`の割当自体は残る。同時に稼働する古いタイマーと不要なコールバックを減らした変更で、割当ゼロという意味ではない。

描画の小さな比較では、8行中2行だけが新しい移動を4回行ったとき、glyph数は旧実装274/218/274/272、新実装70/70/0/0。100・125・150・200%表示で全画素差0を確認した。時間・glyph数・転送量・DOM数はそれぞれ異なる指標で、アプリ全体のFPSや入力遅延の改善率ではない。

## 既知の計測失敗の扱い

CodeLensの旧検査は、各フレームの移動を「そのフレーム間に入った新規入力」だけと比較していた。補間中は過去の入力の残距離も消費するため、正常な追従でも失敗していた。行画像のbaseline位相も含めた実位置を使い、逆行なし・累積入力予算の超過なし・停止後に全入力距離と一致、を検証する。新しい距離一致の検査が、上記の実際の5px不足を検出した。

`touchpad deltas preview`は非アニメーション時の即時preview・要求集約を調べる試験だが、設定が省略され40ms補間の残り要求が次の計測へ混ざっていた。非アニメーション条件を明示し、既存の要求件数・画面位置・最大未完了1件・総距離の検査は維持した。アニメーション有効時はCodeLens・cadence・遅延応答の検査で確認する。

横方向の配布版試験は、160msの停止処理後も移動中の通知だけを待ち続けていた。クリック直前に250ms待つと、修正前のv0.4.0でも再現する。停止後のrestore通知も扱い、先読みの整列と停止済みの端数位置の保持を、ネイティブ列・クリック位置・画素・保存内容で検証する。画素比較中に見つかった単語強調の変化は、上記の製品側の修正に含めた。次の操作にはキャッシュだけで描ける場合があるため、毎回ネイティブの再通知が来るという前提も除いた。
